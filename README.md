# Just4Kids

Current UI and client model (2026-10-16): the dashboard, validation/errors, dates, reports and barber WhatsApp handoff use English with a left-to-right layout. Saved user-entered text is preserved in its original language. Clients have a phone number and addresses; client names, address instructions and latitude/longitude are removed from forms, API contracts, database columns and saved reservation/revision JSON by migrations `0024_remove_client_details` and `0025_remove_client_receipt_details`. Confirmed 2026-10-16 (feature batch P8): a reservation carries **no price, invoice or payment**. The reservation action offers two buttons: **Save reservation** (save and return to today's reservations) and **Save & send via WhatsApp** (save, record the WhatsApp handoff, open WhatsApp for the barber, then return to today's reservations). Confirmed 2026-10-21: the Arabic client-facing WhatsApp AI (OpenWA gateway) only collects booking requests and sends a summary to the staff WhatsApp number; staff book manually. This supersedes older UI/name/location/invoice descriptions below.


English home-visit haircut CRM. Product scope: [docs/project-contract.md](docs/project-contract.md). Working instructions: [AGENTS.md](AGENTS.md).

## Run

```sh
pnpm install --frozen-lockfile
pnpm db:migrate
pnpm dev
```

Web: `http://localhost:3000`. API: `http://127.0.0.1:4000/health`. The web app proxies `/api/*` to Express, so `/api/health` works through the same web origin.

Use one root `.env` based on `.env.example`. API, web configuration, and Drizzle load it; shell/container environment variables take precedence. The API now requires MySQL and the authentication migration before startup so it can create or update the sole administrator. `/health` reports API liveness after startup, not database readiness. The API validates all required authentication and server settings before serving requests.

Set `ADMIN_PHONE` in international format (`+965` followed by eight digits for a Kuwaiti mobile number), `ADMIN_PASSWORD` as plaintext **in the ignored environment file only**, and `AUTH_SECRET` as 32 random bytes encoded as 64 hex characters. The API hashes the password before saving it in MySQL. The local `.env` has the requested editable example phone and `admin1234`; choose a longer unique password before production. Restarting the API after changing the administrator phone/password updates the one administrator and revokes their sessions. Employee credentials and resets are managed only by the administrator. `APP_ORIGIN` must match the browser's web origin exactly, such as `http://localhost:3000` locally.

The browser login flow uses same-origin `/api/auth/csrf` (receive a CSRF token and an HttpOnly pre-login cookie), then `POST /api/auth/login` with `{ "phone": "+96555551234", "password": "..." }` and the token in `X-CSRF-Token`. On success the server sets an HttpOnly, SameSite=Strict session cookie lasting seven days. `GET /api/auth/session` returns the permitted account and a fresh CSRF token; `POST /api/auth/logout` requires that token and revokes the session. The backend returns no bearer token, and the frontend should keep the CSRF token in memory rather than localStorage. The web app implements this flow and keeps the CSRF token in its in-memory query cache.

For production, set `NODE_ENV=production`, use a root `.env.production` based on `.env.production.example`, and run `pnpm build` then `pnpm start`. The API reads `.env.production` in production unless `ENV_FILE` selects another root environment filename. The example binds a directly run API to `127.0.0.1`; Docker Compose overrides `HOST` to `0.0.0.0` inside the private container network. Configure HTTPS `APP_ORIGIN`, a unique administrator password (not the template value), and a random `AUTH_SECRET`. VPS deployment is a later step.

## Database

Set `DATABASE_URL` in the root `.env` for the existing MySQL instance on port 3306. Docker uses `DOCKER_DATABASE_URL`, pointing to the Compose `db` service. URL-encode special characters in credentials.

Development database: `just4kids`. Test database: `just4kids_test`, selected by `.env.test`. These databases are separate from the database belonging to the project the credentials were copied from.

```sh
pnpm db:generate
pnpm db:migrate
pnpm db:migrate:test
pnpm db:studio
```

Migrations live in `packages/db/drizzle` and apply in order. They cover accounts, sessions and login limits (`0000`); branches and employees (`0001`); weekly hours and dated exceptions (`0002`); clients and addresses (`0003`); reservations, visit history and revisions (`0004`–`0006`); barber photos (`0008`); special-needs child counts (`0009`); client status history (`0010`); salon entries (`0012`–`0013`); booking notes, extra address fields, barber-seen time, account expiry and WhatsApp-to-barber messages (`0014`–`0018`); barber daily collections (`0020`); removal of branches from barbers and bookings (`0021`); manual locks (`0022`); managed areas (`0023`); removal of client names/instructions/coordinates (`0024`–`0025`); replacement of branch prices and location with a branch address (`0026`–`0028`); weekday active switches (`0029`); and removal of reservation invoices and payments (`0030_drop_reservation_money`). The account table enforces one administrator and unique phone numbers, and sessions store only hashes of random cookie tokens. Money (barber collections and salon entries) is stored as exact three-decimal KWD. Generate new migrations after adding later feature tables; migration/studio commands require the configured database. Never add `.env` credentials to Git.

The branch API is administrator-only: `GET/POST /api/branches` and `GET/PATCH /api/branches/:id`. A branch has only a `name` and an `address`; branches exist only to group salon daily entries. The employee API supports administrator `GET/POST /api/employees`, `GET/PATCH /api/employees/:id`, and `POST /api/employees/:id/reset-password`. Employees may `GET /api/employees/me`, `GET` their own ID, and `PATCH /api/employees/me` with only `displayName`. Barbers have no branch (migration 0021). Administrator phone changes, disabling, and password resets are protected by role checks; phone/disable/reset actions revoke affected employee sessions. All browser writes require the current session's `X-CSRF-Token` and matching `APP_ORIGIN`. The dashboard provides branch, barber, password-reset, and own-profile screens.

Barber photos are administrator-only writes and any signed-in read: `PUT /api/employees/:id/photo` accepts a raw JPEG/PNG/WEBP body up to 2 MB and re-encodes it to a 512 px square JPEG; `DELETE /api/employees/:id/photo` removes it; `GET /api/employees/:id/photo` serves the stored image (404 `PHOTO_NOT_FOUND` when absent) and requires session authentication. Files are stored under `UPLOADS_DIR` (default `uploads`, `/app/uploads` in Compose) by employee ID only, never from a caller-supplied path; the photo shown for a booking is always the barber's current photo, keyed by the assigned barber ID. Uploads decode through `sharp` with `sharp.concurrency(1)` and a 24 MP input cap so a large photo cannot exhaust the API's memory. Each upload stores `photoUpdatedAt`, and the dashboard appends `?v=<photoUpdatedAt>` so a replaced photo is fetched fresh. Reads and writes need no dependency beyond `sharp`; the directory must be persistent and writable by the `node` user (the API image pre-creates `/app/uploads` owned by `node`; see Backups).

The schedule API supports administrator `PUT /api/schedules/:employeeId/weekly` with `{ "days": [{ "dayOfWeek": 1, "active": true, "intervals": [{ "startTime": "09:00", "endTime": "13:00" }] }] }`, replacing the full weekly plan. Weekdays run Sunday `0` through Saturday `6`; an omitted day is closed. `active: false` keeps a day's shifts but accepts no bookings or locks; turning a day off is refused while the barber has a future booking on that weekday, and a dated exception still opens that date. `PUT /api/schedules/:employeeId/exceptions/:date` with `{ "intervals": [] }` closes that Kuwait date, or supplies special hours; `DELETE` on the same path restores weekly hours. Administrators can read any `GET /api/schedules/:employeeId`; employees can read only their own ID or `GET /api/schedules/me`. `GET /api/availability/eligible?date=YYYY-MM-DD&startTime=HH:mm&endTime=HH:mm` is administrator-only and returns eligible enabled barbers and `timeZone: "Asia/Kuwait"`. Windows must stay within one local day and last 20–240 minutes inclusive; touching windows are allowed. Schedule writes require origin and session CSRF protection. The dashboard provides weekly-hours/exception editors, the barber’s own schedule view, and eligible-barber selection during booking. Eligibility checks saved reservations: booked/arrived/completed block the original window, while cancelled/no-show release it. Weekly edits, exception replacement, and exception deletion return `SCHEDULE_BOOKING_CONFLICT` (409) and roll back if a blocking booking whose reserved end is still in the future in Kuwait would no longer fit; ended bookings retain their historical records and do not prevent schedule edits. Schedule changes and reservation creation hold the same account/employee locks.

Manual locks (S3, migration `0022_open_valkyrie`; flexible length since P6): administrator `POST /api/schedules/:employeeId/blocks` accepts `{ "date": "YYYY-MM-DD", "startTime": "13:00", "endTime": "14:30", "reason": "optional, at most 500 characters" }` and returns 201 with the lock ID, reason, creator and timestamp. Start and end must be whole half-hours on the same day with the end after the start; the lock must be in the future in Kuwait, fit working hours, and not overlap a blocking booking or another lock. `DELETE /api/schedules/:employeeId/blocks/:blockId` removes only that barber's manual lock (204; 404 if absent). Both writes require administrator role, matching origin and session CSRF. Schedule responses include `blocks`; employees read only their own. Locks block eligibility, booking creation, reservation edits/reassignment and visit restoration under the same employee locks as bookings; an occupied or unavailable time returns `TIME_BLOCK_CONFLICT` (409). The booking pills' lock mode sets a start pill and an end pill; manual locks show blue with their reason. No client or booking is created, and unlocking does not change weekly hours or exceptions.

The client API is administrator-only: `GET/POST /api/clients`, `GET/PATCH /api/clients/:id`, `GET /api/clients/lookup?phone=%2B96555550101`, `POST /api/clients/:id/addresses`, and `PATCH /api/clients/:id/addresses/:addressId`. URL-encode the leading `+` in phone lookup queries. Search uses `GET /api/clients?q=...&limit=20&offset=0` and returns `{ clients, total, limit, offset }`. Creating a client requires `{ "phone": "+96555550101", "address": { "area": "Hawally", "block": "3", "street": "Street 5", "houseNumber": "12" } }`; `buildingName` may replace `houseNumber`. Addresses may also include `floor`, `apartment`, `avenue`, `gate`, `blueNumber`, or a Google Maps `mapsUrl`. Client names, barber instructions and coordinates are not accepted. One client owns each exact international phone; duplicate phones return `PHONE_ALREADY_USED` (409). The web phone inputs accept a bare Kuwaiti eight-digit number and save it as `+965…`; other country codes still use `+`. Client creation saves the initial address atomically. Nested address edits require the matching client ID; writes require the session CSRF token and matching origin. Reservation creation snapshots the selected address and client contact so later edits preserve historical details. Clients have an active/stopped state: `PATCH /api/clients/:id/status` accepts `{ "enabled": false, "reason": "required reason" }` (administrator + CSRF) and records the change in history (`CLIENT_STATUS_UNCHANGED`, 409, when the state already matches); `GET /api/clients/:id/status-events` returns `{ events }`; `GET /api/clients?status=all|active|stopped` filters. A stopped client cannot receive a new booking (409 `CLIENT_DISABLED`); existing bookings and reads are unaffected. The dashboard provides client search with a status filter and badge, creation, editing, address management, and a stop/reactivate dialog with a status-history card.

Phone-first booking (S9): `/bookings/new` looks up an international phone through `GET /api/clients/lookup?phone=...` (eight local Kuwaiti digits are normalized on the web). The lookup response includes `lastUsedAddressId`, selected from the most recently created booking, or the newest saved address when there is no booking history. Existing clients select their saved address; stopped clients cannot be booked. Only a lookup 404 opens the inline new-client fields; lookup errors require retry, and changing the phone clears any previous selection. For an unknown phone, administrator `POST /api/bookings/with-client` accepts the ordinary booking fields without `clientId`/`addressId`, plus `client: { phone, address }` with a required active `address.areaId`. The new client, address, reservation and initial history are saved in one transaction under the same barber/availability rules as ordinary bookings. Failures roll back everything, and a concurrently registered phone returns `PHONE_ALREADY_USED` (409) rather than overwriting a client. Both booking endpoints require administrator role, matching origin and session CSRF. Clients are identified by phone only. Migration `0024_remove_client_details` drops client names, address instructions and coordinates, including their saved booking/revision values.

Managed areas (S6, migration `0023_tearful_next_avengers`): administrator `GET /api/areas?q=...&status=all|active|stopped` returns `{ areas }`; `POST /api/areas` accepts `{ "name": "الفنطاس" }`; `PATCH /api/areas/:id` accepts `name` and/or `enabled` to rename, stop or reactivate an area. Names are trimmed, limited to 120 characters, and unique (`AREA_NAME_EXISTS`, 409). Writes require matching origin and session CSRF. `/areas` manages the catalogue, which starts empty; add the required areas before creating new dashboard addresses. The client/address forms search active names and submit both `area` and optional `areaId`. The API checks the selected identity, name and active state under the address transaction (`AREA_UNAVAILABLE`, 409, if changed/stopped), so failed client creation leaves no partial client. Saved addresses and booking snapshots retain their text when catalogue names change. An existing free-text/stopped area may be kept while editing its address. Legacy API callers can still send free-text `area` without `areaId`; no geographic service-area restriction is introduced.

The booking API supports administrator `POST /api/bookings` with `{ "clientId": "<uuid>", "addressId": "<uuid>", "employeeId": "<uuid>", "date": "YYYY-MM-DD", "startTime": "09:00", "endTime": "09:20", "adultCount": 3, "childCount": 0 }`. Counts are integers from 0 through 2,147,483,647 with at least one haircut; `specialChildCount` (optional, default 0) records a subset of the children and must not exceed `childCount`; `notes` is optional (up to 1,000 characters). A reservation carries no price, invoice or payment. The selected address must belong to the client. The start must be strictly in the future in Kuwait, with no extra cutoff. The 20–240 minute window is independent of counts. Creation rechecks enabled status, working hours, exceptions, locks and blocking visits under employee locks, then saves the reservation and its initial history atomically. It returns 201 with a `J4K-` reference and historical client/address/barber snapshots only after commit. The source cannot be supplied by browser callers. Missing records return 404, invalid input or a non-future start returns 400 (`INVALID_INPUT` or `BOOKING_START_NOT_FUTURE`), a stopped client returns `CLIENT_DISABLED` (409), and conflicts/disabled barbers return `BARBER_UNAVAILABLE` (409). Writes require origin and session CSRF protection.

`GET /api/bookings?limit=20&offset=0` returns `{ bookings, total, limit, offset }` in descending visit-date/window order and also accepts `date` and `employeeId` filters. `GET /api/bookings/:id` returns the booking with its `visitVersion`. Administrator reads cover all records; employee lists are scoped to their own bookings, and another employee's direct booking ID returns 403. New records use visit `booked` and version `0`. `POST /api/bookings/:id/sent-to-barber` (administrator + CSRF) records the WhatsApp handoff to the barber and returns 201; it appears in the booking tracking report. Reservations created in the dashboard have source `manual`. The `ai` source and the internal trusted-sender creation path have no caller since the WhatsApp AI became intake-only (2026-10-21); their removal is planned with phase 12.

The visit API supports `POST /api/bookings/:id/visit` with `{ "status": "arrived", "expectedVersion": 0, "reason": "optional nonempty reason" }` for the administrator or assigned employee. From `booked`, normal actions are `arrived`, `cancelled`, or `no_show`; from `arrived`, they are `completed`, `cancelled`, or `no_show`. Arrival/completion require the reserved start to have been reached; no-show requires the end to have been reached, using Kuwait local time. Cancellation is allowed from booked/arrived without an extra cutoff. Employees cannot change terminal states, reschedule, or reassign. `POST /api/bookings/:id/visit/correction` is administrator-only, accepts any target visit state with `{ "status": "booked", "expectedVersion": 1, "reason": "required correction reason" }`, and rechecks enabled status, working hours/exceptions, and conflicts before restoring a blocking state. Both routes require origin/CSRF protection and return the updated booking with the next version only after the visit and its history commit together.

`GET /api/bookings/:id/history` returns `{ events }` in version order, covering creation and every action/correction with previous/new visit status, actor identity/type, UTC timestamp, reason, and correction flag. Administrator/assigned-employee ownership applies. New manual bookings record an administrator creation event. Old records receive a migration-time system baseline with a note that earlier details are unavailable. `VISIT_CONFLICT` (409) means the caller's version is stale and they must reload; `INVALID_VISIT_TRANSITION` and `VISIT_TOO_EARLY` also return 409. Invalid payloads/blank correction reasons return 400; unauthorized actors return 403. A restore conflict returns `BARBER_UNAVAILABLE` (409). The original window is preserved. The internal client-cancellation service (`CLIENT_CANCELLATION_NOT_ALLOWED`) has no caller since WhatsApp booking changes were dropped (2026-10-21); its removal is planned with phase 12.

Administrator-only `PATCH /api/bookings/:id` accepts a partial edit such as `{ "expectedVersion": 0, "startTime": "10:00", "endTime": "10:20", "adultCount": 2, "reason": "optional nonempty reason" }`. Editable fields are `addressId`, `employeeId`, `date`, `startTime`, `endTime`, `adultCount`, `childCount`, `specialChildCount`, and `notes`; at least one is required. A booked visit that has not started is a reservation edit, and its resulting start must remain strictly in the future. A started or finished visit (no longer `booked`, or its start has passed) is a correction: it requires a `reason`, may be moved into the past, and still rechecks working hours and conflicts. Source/client identity/status cannot be supplied. Window/barber changes recheck working hours, exceptions, enabled status, locks and conflicts under shared employee locks. A supplied address must belong to the client and snapshots its current saved details; omitted address/barber fields preserve historical snapshots. The transaction retains the booking/reference and saves complete before/after snapshots with actor/time/reason.

`GET /api/bookings/:id/revisions` returns `{ revisions }` ordered by version, for the administrator or current assigned employee. Reassignment removes the former employee's access to all booking details and histories. `visitVersion` advances for edits and visit actions; send its latest value as `expectedVersion`. Versions in individual visit-event/revision lists can have gaps. Invalid merged counts/windows return `INVALID_INPUT` (400); a reservation edit to a non-future start returns `BOOKING_START_NOT_FUTURE` (400); unavailable windows/barbers return `BARBER_UNAVAILABLE` (409). Stale edits return `BOOKING_CONFLICT` (409); a correction without a reason returns `CORRECTION_REASON_REQUIRED` (400); unchanged edits return `BOOKING_UNCHANGED` (409). Missing records return 404 and employee edits return 403. Browser writes require origin/CSRF protection. Any failure rolls back the reservation and revision together. The dashboard provides the administrator edit dialog and revision history.

Barber daily collections (S11, migration `0020`): `GET /api/collections?from=&to=&employeeId=` returns `{ timeZone, from, to, entries, totals }`; a barber reads only their own. Administrator-only `POST /api/collections` records one entry per barber and day with `{ "employeeId": "<uuid>", "date": "YYYY-MM-DD", "normalChildren": 2, "specialChildren": 0, "cash": "5.000", "link": "0.000", "knet": "2.000" }` (counts and amounts default to zero; the server computes `total`), `PATCH /api/collections/:id` applies a subset edit with the entry's `expectedVersion`, and `GET /api/collections/:id/history` returns before/after events with actor and time. Writes require origin/session CSRF. Amounts are exact three-decimal KWD strings. These daily rows are the only barber money; reservations carry none.

The salon API is administrator-only: `GET /api/salon?from=&to=&branchId=` returns `{ entries, totals }` for the period, `POST /api/salon` creates one entry per branch and date with `{ "branchId": "<uuid>", "date": "YYYY-MM-DD", "childCount": 3, "cash": "5.000", "link": "1.000", "knet": "2.000" }` (amounts default to `0.000`; the server computes `total`), `PATCH /api/salon/:id` applies a subset edit (requiring the entry's `expectedVersion`) and recomputes the total, and `GET /api/salon/:id/history` returns the before/after events. A duplicate branch+date returns `SALON_ENTRY_EXISTS` (409), a stale version returns `SALON_ENTRY_CONFLICT` (409), and a no-op edit returns `SALON_ENTRY_UNCHANGED` (409); unknown entries/branches return 404, invalid amounts return 400, and a total that overflows the stored precision returns `SALON_TOTAL_TOO_LARGE` (400). Writes require origin/session CSRF. `GET /api/reports/comprehensive?from=&to=` (administrator-only; period only, like the old report, so a `branchId` is rejected) returns `barbers`, one `salon` row, and `totals`, each with per-method `{ count, total }` money, a `collected` total, and a one-decimal `share` of the combined collected total.

Reports (phase 9) are read-only and available to the administrator and employees: `GET /api/reports/reservations` and `GET /api/reports/haircuts`. Both accept `dateBasis` (`visit_date`, the default, or `created_date`, the Kuwait day the reservation was made), inclusive `from`/`to` dates, `employeeId`, `clientId`, `status`, `source` (`manual`/`ai`), and `q` (reference or saved client phone). The reservations report also takes `limit` (1–100, default 20) and `offset`, and returns `{ dateBasis, timeZone, summary, bookings, total, limit, offset }`: the summary counts reservations by visit status and source, plus edited reservations/edits and corrected reservations/status corrections; each booking adds `editCount` and `correctionCount`. The haircut report returns adult/child/special-needs quantities as `totals`, `byDate`, and `byEmployee`, each with `bookings`, `reserved` (all matching reservations), `completed`, `open` (booked/arrived), `cancelled`, and `noShow`. Completed quantities come from visit status. Work stays with the barber currently assigned to the reservation; rows show current barber names. Employees always receive only reservations currently assigned to them, and filtering by another barber returns 403. Invalid filters return `INVALID_INPUT` (400).

The barber report (phase 10) uses the same filters and access rules: `GET /api/reports/employees`. Each row has `work` (the haircut measures above plus `completedVisits` and `reservedMinutes`) and `cash`, read from the administrator's daily barber collections as `{ count, total, byMethod: { cash, link, knet } }`; collections follow only the period and barber filters, so `cash` is `null` when a client, status, source, or search filter is applied. Money totals are exact three-decimal KWD strings. Reserved minutes cover booked/arrived/completed windows and include travel; cancelled and no-show visits release their window. Barber rows add `enabled` and `availableMinutes`: scheduled working minutes from weekly hours and dated exceptions for every day from `from` to `to`, or `null` unless the visit-date basis has both dates. Employees see only their own row. `GET /api/reports/clients` returns each client's phone and the same `work` measures (completed visits above one are repeat visits). Individual records come from `GET /api/reports/reservations` with the same filters. The administrator-only salon report (`GET /api/salon`) and comprehensive report (`GET /api/reports/comprehensive`) group collected money by payment method with totals and shares. The administrator-only booking tracking report `GET /api/reports/tracking?from=&to=&employeeId=&clientId=` returns each matching booking (by Kuwait visit date, newest first) with its full timeline oldest first: visit status changes and corrections, reservation revisions, and WhatsApp sends to the barber, each with actor name/role, time, and reason; with no period it covers the current Kuwait week (Saturday–Friday), a lone `from` or `to` covers 7 days from or up to that day, and a period longer than 31 days returns 400.

Employee login now rechecks the verified phone as well as enabled status and password hash while locking the account before session creation. An in-progress login with the old phone is rejected if an administrator changes the phone before that step.

## Web dashboard

`apps/web` is an English-only, left-to-right Next.js dashboard for the implemented backend (phases 1–11). Screens: login; bookings list/detail/new booking, visit actions, administrator corrections and edits, history tabs, and the WhatsApp handoff to the barber; clients and addresses; managed areas; barbers with weekly hours, weekday switches, dated exceptions and locks; branches (for salon entries); the barber’s own schedule and profile; barber daily collections (`/collections`); salon daily entries (`/salon`); and reports (`/reports`): bookings with a summary and linked records, haircuts by date/barber, barber performance with reserved versus scheduled hours, client history, the administrator-only booking tracking timeline (`/reports/tracking`), and the administrator-only salon report and comprehensive collections report. Report filters (date basis, range, barber, client, status, source, search) live in the page address and are printed with the report. Employees see only their own bookings and pages; administrator pages show a clear message if opened directly by an employee. The API remains authoritative for every rule.

Design system:

- Tokens live in `apps/web/src/app/globals.css` as CSS variables for light (`:root`) and dark (`.dark`) themes, mapped to Tailwind with `@theme inline`. Components use token classes only (`bg-card`, `text-muted-foreground`, `bg-status-booked-soft`, …), never raw colors. Brand colors: teal primary, sun-yellow accent, cool mist background.
- Typeface: Readex Pro (Latin + Arabic for saved user content), bundled through `@fontsource-variable/readex-pro` with no external font request. Digits are Western (0–9); phones, amounts, and references render left-to-right with bidirectional isolation through the `Ltr` component.
- UI primitives are shadcn/ui (Radix) components in `apps/web/src/components/ui`, configured by `apps/web/components.json` with `rtl: false`. Add more with `pnpm dlx shadcn@4.21.0 add <name>` from `apps/web`, then check the import path (`@/lib/utils`) and LTR behaviour.
- Theme: light, dark, or system, via `next-themes`. Print styles always use the light palette.
- Data: TanStack Query hooks in `apps/web/src/lib/api/hooks.ts` call the same-origin `/api` proxy, attach the session CSRF token to writes, sign out on 401, and reload a booking after stale-version conflicts. Forms use react-hook-form with English Zod schemas in `apps/web/src/lib/forms.ts`, built on the shared contracts.
- Money is computed in integer fils (`lib/money.ts`); dates and times are Kuwait-local (`lib/kuwait-time.ts`).

## Docker

`docker.web` builds the Next.js standalone server; `docker.api` builds and packages the Express API with production dependencies. Each image copies only its own app and the packages it uses, installs from manifests first, and keeps the pnpm store (and the Next.js build cache) in BuildKit cache mounts, so an API-only change does not rebuild web, a web-only change does not rebuild the API, and docs/tests edits rebuild nothing. A lockfile change reinstalls dependencies for both. Both run as non-root users. `.dockerignore` excludes secrets and local build/dependency artifacts.

```sh
pnpm docker:up
pnpm docker:down
```

Compose runs its own MySQL 8 container (`db`, data in the `db-data` volume), a one-off `migrate` service that applies Drizzle migrations on every `up`, then the API and web. Following the VPS port convention (web `30x0`, API `40x0`), web is published on `127.0.0.1:3030` for a host reverse proxy and the API on `127.0.0.1:4030` for host-only checks; set `WEB_BIND_ADDRESS`/`WEB_PORT` or `API_BIND_ADDRESS`/`API_PORT` if needed. MySQL is not published to the host. Each service has a memory cap (`db` 768 MB, `migrate` 512 MB, `api` and `web` 384 MB each) so one runaway container cannot exhaust the shared VPS. On the server, `scripts/deploy.sh +965XXXXXXXX` creates `.env.production` with random secrets on the first run (and prints the administrator password once), then builds and starts everything; later runs keep the existing file. Compose needs `DB_PASSWORD`, `DB_ROOT_PASSWORD`, `DOCKER_DATABASE_URL`, and `API_ENV_FILE=.env.production` from that file; the `docker:*` scripts pass it with `--env-file`.

The internal API address is a web build argument, so rebuild web when changing it. Docker is required for image builds and Compose execution.

### Backups

Two named volumes hold state that is not in Git and must both be backed up: `db-data` (MySQL) and `uploads-data` (barber photos under `UPLOADS_DIR=/app/uploads`). `scripts/deploy.sh` documents the per-volume `tar` backup and restore commands in its header; stop the stack before archiving so the MySQL data directory is consistent (or take a logical `mysqldump`), and restore both volumes into a fresh host while the stack is stopped. A database-only backup is incomplete because it omits the photos.
