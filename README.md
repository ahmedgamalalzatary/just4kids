# Just4Kids

Arabic home-visit haircut CRM. Product scope: [docs/project-contract.md](docs/project-contract.md). Working instructions: [AGENTS.md](AGENTS.md).

## Workspace

```text
apps/web             Next.js + React + Tailwind, Arabic RTL
apps/api             Express API
packages/contracts   Shared Zod schemas and TypeScript types
packages/db          Drizzle + mysql2, schema and migrations
packages/config      Shared ESLint and TypeScript configuration
```

Requirements: Node 24 and pnpm 12.4.1. Versions are pinned in `pnpm-workspace.yaml` and `pnpm-lock.yaml`.

## Run

```sh
pnpm install --frozen-lockfile
pnpm db:migrate
pnpm dev
```

Web: `http://localhost:3000`. API: `http://127.0.0.1:4000/health`. The web app proxies `/api/*` to Express, so `/api/health` works through the same web origin.

Use one root `.env` based on `.env.example`. API, web configuration, and Drizzle load it; shell/container environment variables take precedence. The API now requires MySQL and the authentication migration before startup so it can create or update the sole administrator. `/health` reports API liveness after startup, not database readiness. The API validates all required authentication and server settings before serving requests.

Set `ADMIN_PHONE` in international format (`+965` followed by eight digits for a Kuwaiti mobile number), `ADMIN_PASSWORD` as plaintext **in the ignored environment file only**, and `AUTH_SECRET` as 32 random bytes encoded as 64 hex characters. The API hashes the password before saving it in MySQL. The local `.env` has the requested editable example phone and `admin1234`; choose a longer unique password before production. Restarting the API after changing the administrator phone/password updates the one administrator and revokes their sessions. Employee credentials and resets are managed only by the administrator. `APP_ORIGIN` must match the browser's web origin exactly, such as `http://localhost:3000` locally.

The browser login flow uses same-origin `/api/auth/csrf` (receive a CSRF token and an HttpOnly pre-login cookie), then `POST /api/auth/login` with `{ "phone": "+96555551234", "password": "..." }` and the token in `X-CSRF-Token`. On success the server sets an HttpOnly, SameSite=Strict session cookie lasting seven days. `GET /api/auth/session` returns the permitted account and a fresh CSRF token; `POST /api/auth/logout` requires that token and revokes the session. The backend returns no bearer token, and the frontend should keep the CSRF token in memory rather than localStorage. The web app implements this flow and keeps the CSRF token in its in-memory query cache.

For production, set `NODE_ENV=production`, use a root `.env.production` based on `.env.production.example`, and run `pnpm build` then `pnpm start`. The API reads `.env.production` in production unless `ENV_FILE` selects another root environment filename. The example binds a directly run API to `127.0.0.1`; Docker Compose overrides `HOST` to `0.0.0.0` inside the private container network. Configure HTTPS `APP_ORIGIN`, a unique administrator password (not the template value), and a random `AUTH_SECRET`. VPS deployment is a later step.

## Database

Set `DATABASE_URL` in the root `.env` for the existing MySQL instance on port 3306. Docker uses `DOCKER_DATABASE_URL`, pointing to the Compose `db` service. URL-encode special characters in credentials.

Development database: `just4kids`. Test database: `just4kids_test`, selected by `.env.test`. These databases are separate from the database belonging to the project the credentials were copied from.

```sh
pnpm db:generate
pnpm db:migrate
pnpm db:migrate:test
pnpm db:studio
```

The first migration creates accounts, sessions, and login-attempt limits. The second creates branches and employee profiles. The third creates weekly work intervals and dated exceptions. The fourth creates clients and reusable service addresses. The fifth (`0004_brown_the_fallen.sql`) creates reservations and their single invoices with historical snapshots. The sixth (`0005_old_dragon_man.sql`) adds visit versions/history and records a system baseline for existing reservations without inventing their earlier transition details. The seventh (`0006_nice_romulus.sql`) adds immutable reservation/invoice edit revisions. The eighth (`0007_married_stark_industries.sql`) adds cash receipts/events with one active receipt per invoice. The ninth (`0008_robust_misty_knight.sql`) adds an optional `photo_updated_at` on employees, used to version the barber-photo address so a replacement is not served from a browser cache. The tenth (`0009_cynical_abomination.sql`) adds `bookings.special_child_count` (default 0, bounded by the child count) and extends the counts check. The eleventh (`0010_rainy_joshua_kane.sql`) adds `clients.enabled` and the `client_status_events` history table. The twelfth (`0011_narrow_virginia_dare.sql`) adds a `method` enum (`cash`/`link`/`knet`, default `cash`) to `cash_payments` and `cash_payment_events`, so receipts recorded before the change are treated as cash. The thirteenth (`0012_certain_carlie_cooper.sql`) adds `salon_entries` (one per branch and day: child count, cash/link/KNET amounts, computed total, entered-by) and its `salon_entry_events` history. The fourteenth (`0013_rare_demogoblin.sql`) adds a `version` to `salon_entries` for optimistic concurrency. The account table enforces one administrator and unique phone numbers, and sessions store only hashes of random cookie tokens. Branch adult/child prices are exact `DECIMAL(12,3)` KWD strings; invoice line amounts/totals use `DECIMAL(24,3)` and BigInt fils arithmetic. Haircut durations are descriptive minutes. Generate new migrations after adding later feature tables; migration/studio commands require the configured database. Never add `.env` credentials to Git.

The branch API supports administrator `GET/POST /api/branches` and `GET/PATCH /api/branches/:id`. Branch writes accept `name`, `location`, `adultPrice`, `childPrice`, `adultDurationMinutes`, and `childDurationMinutes`; prices such as `"5.5"` return as `"5.500"`. The employee API supports administrator `GET/POST /api/employees`, `GET/PATCH /api/employees/:id`, and `POST /api/employees/:id/reset-password`. Employees may `GET /api/employees/me`, `GET` their own ID, and `PATCH /api/employees/me` with only `displayName`. Barbers have no branch (migration 0021); branches exist only for salon daily entries. Administrator phone changes, disabling, and password resets are protected by role checks; phone/disable/reset actions revoke affected employee sessions. All browser writes require the current session's `X-CSRF-Token` and matching `APP_ORIGIN`. The dashboard provides branch, barber, password-reset, and own-profile screens.

Barber photos are administrator-only writes and any signed-in read: `PUT /api/employees/:id/photo` accepts a raw JPEG/PNG/WEBP body up to 2 MB and re-encodes it to a 512 px square JPEG; `DELETE /api/employees/:id/photo` removes it; `GET /api/employees/:id/photo` serves the stored image (404 `PHOTO_NOT_FOUND` when absent) and requires session authentication. Files are stored under `UPLOADS_DIR` (default `uploads`, `/app/uploads` in Compose) by employee ID only, never from a caller-supplied path; the photo shown for a booking is always the barber's current photo, keyed by the assigned barber ID. Uploads decode through `sharp` with `sharp.concurrency(1)` and a 24 MP input cap so a large photo cannot exhaust the API's memory. Each upload stores `photoUpdatedAt`, and the dashboard appends `?v=<photoUpdatedAt>` so a replaced photo is fetched fresh. Reads and writes need no dependency beyond `sharp`; the directory must be persistent and writable by the `node` user (the API image pre-creates `/app/uploads` owned by `node`; see Backups).

The schedule API supports administrator `PUT /api/schedules/:employeeId/weekly` with `{ "days": [{ "dayOfWeek": 1, "intervals": [{ "startTime": "09:00", "endTime": "13:00" }] }] }`, replacing the full weekly plan. Weekdays run Sunday `0` through Saturday `6`; an omitted day is closed. `PUT /api/schedules/:employeeId/exceptions/:date` with `{ "intervals": [] }` closes that Kuwait date, or supplies special hours; `DELETE` on the same path restores weekly hours. Administrators can read any `GET /api/schedules/:employeeId`; employees can read only their own ID or `GET /api/schedules/me`. `GET /api/availability/eligible?date=YYYY-MM-DD&startTime=HH:mm&endTime=HH:mm` is administrator-only and returns eligible enabled barbers and `timeZone: "Asia/Kuwait"`. Windows must stay within one local day and last 20–240 minutes inclusive; touching windows are allowed. Schedule writes require origin and session CSRF protection. The dashboard provides weekly-hours/exception editors, the barber’s own schedule view, and eligible-barber selection during booking. Eligibility now checks saved reservations: booked/arrived/completed block the original window, while cancelled/no-show release it. Weekly edits, exception replacement, and exception deletion return `SCHEDULE_BOOKING_CONFLICT` (409) and roll back if a blocking booking whose reserved end is still in the future in Kuwait would no longer fit; ended bookings retain their historical records and do not prevent schedule edits. Schedule changes and reservation creation hold the same account/employee locks.

Manual half-hour locks (S3, migration `0022_open_valkyrie`): administrator `POST /api/schedules/:employeeId/blocks` accepts `{ "date": "YYYY-MM-DD", "startTime": "13:00", "reason": "optional, at most 500 characters" }`; the server computes `endTime` as 30 minutes later and returns 201 with the lock ID, reason, creator and timestamp. Starts must be on `:00` or `:30`, future in Kuwait, within working hours and end before midnight. `DELETE /api/schedules/:employeeId/blocks/:blockId` removes only that barber's manual lock (204; 404 if absent). Both writes require administrator role, matching origin and session CSRF. Schedule responses include `blocks`; employees read only their own. Locks block eligibility, manual/AI creation, reservation edits/reassignment and visit restoration under the same employee locks as bookings; an occupied or unavailable time returns `TIME_BLOCK_CONFLICT` (409). The booking pills' «قفل / فتح الأوقات» mode manages half-hours separately from visit length; manual locks show blue with their reason. No client, booking or invoice is created, and unlocking does not change weekly hours or exceptions.

The client API is administrator-only: `GET/POST /api/clients`, `GET/PATCH /api/clients/:id`, `GET /api/clients/lookup?phone=%2B96555550101`, `POST /api/clients/:id/addresses`, and `PATCH /api/clients/:id/addresses/:addressId`. URL-encode the leading `+` in phone lookup queries. Search uses `GET /api/clients?q=...&limit=20&offset=0` and returns `{ clients, total, limit, offset }`. Creating a client requires `{ "name": "مريم", "phone": "+96555550101", "address": { "area": "حولي", "block": "3", "street": "شارع 5", "houseNumber": "12" } }`; `buildingName` may replace `houseNumber`. Addresses may also include `floor`, `apartment`, `avenue`, `gate`, `blueNumber`, `instructions`, a Google Maps `mapsUrl`, or paired string coordinates `latitude`/`longitude` from a WhatsApp location. One client owns each exact international phone; duplicate phones return `PHONE_ALREADY_USED` (409). The web phone inputs accept a bare Kuwaiti eight-digit number and save it as `+965…`; other country codes still use `+`. Client creation saves the initial address atomically. Nested address edits require the matching client ID; writes require the session CSRF token and matching origin. Reservation creation snapshots the selected address and client contact so later edits preserve historical details. Clients have an active/stopped state: `PATCH /api/clients/:id/status` accepts `{ "enabled": false, "reason": "required reason" }` (administrator + CSRF) and records the change in history (`CLIENT_STATUS_UNCHANGED`, 409, when the state already matches); `GET /api/clients/:id/status-events` returns `{ events }`; `GET /api/clients?status=all|active|stopped` filters. A stopped client cannot receive a new booking (409 `CLIENT_DISABLED`); existing bookings and reads are unaffected. The dashboard provides client search with a status filter and badge, creation, editing, address management, and a stop/reactivate dialog with a status-history card.

The booking API supports administrator `POST /api/bookings` with `{ "clientId": "<uuid>", "addressId": "<uuid>", "employeeId": "<uuid>", "date": "YYYY-MM-DD", "startTime": "09:00", "endTime": "09:20", "adultCount": 3, "childCount": 0 }`. Counts are integers from 0 through 2,147,483,647 with at least one haircut; `specialChildCount` (optional, default 0) records a subset of the children and must not exceed `childCount`, and the administrator types the visit price as `amountCash` and `amountLink` (KWD; the invoice total is their sum). The selected address must belong to the client. The start must be strictly in the future in Kuwait, with no extra cutoff. The 20–240 minute window is independent of counts and descriptive haircut durations. Creation rechecks enabled status, working hours, exceptions, and blocking visits under employee locks, then saves one reservation and one invoice atomically. It returns 201 with a `J4K-` reference, historical client/address/barber snapshots, and a nested invoice only after commit. The source cannot be supplied by browser callers. Missing records return 404, invalid input or a non-future start returns 400 (`INVALID_INPUT` or `BOOKING_START_NOT_FUTURE`), and conflicts/disabled barbers return `BARBER_UNAVAILABLE` (409). Writes require origin and session CSRF protection.

`GET /api/bookings?limit=20&offset=0` returns `{ bookings, total, limit, offset }` in descending visit-date/window order. `GET /api/bookings/:id` returns the booking with its invoice and `visitVersion`; `GET /api/bookings/:id/invoice` returns print-ready invoice data, including reference, issue time, quantities, the typed cash and link amounts, total, and saved client/address/barber details. Administrator reads cover all records; employee lists are scoped to their own bookings, and another employee's direct booking/invoice ID returns 403. New records use visit `booked`, version `0`, invoice `issued`, payment `unpaid`, currency `KWD`, and no tax. Cash payment recording is described below; the dashboard provides booking lists/details and a browser-printable invoice page. The shared internal creation service also accepts trusted WhatsApp sender context and assigns AI source itself; provider wiring/idempotency remain phase 12 work.

The visit API supports `POST /api/bookings/:id/visit` with `{ "status": "arrived", "expectedVersion": 0, "reason": "optional nonempty reason" }` for the administrator or assigned employee. From `booked`, normal actions are `arrived`, `cancelled`, or `no_show`; from `arrived`, they are `completed`, `cancelled`, or `no_show`. Arrival/completion require the reserved start to have been reached; no-show requires the end to have been reached, using Kuwait local time. Cancellation is allowed from booked/arrived without an extra cutoff. Employees cannot change terminal states, reschedule, or reassign. `POST /api/bookings/:id/visit/correction` is administrator-only, accepts any target visit state with `{ "status": "booked", "expectedVersion": 1, "reason": "required correction reason" }`, and rechecks enabled status, working hours/exceptions, and conflicts before restoring a blocking state. Both routes require origin/CSRF protection and return the updated booking with the next version only after visit/invoice/history commit together.

`GET /api/bookings/:id/history` returns `{ events }` in version order, covering creation and every action/correction with previous/new visit and invoice statuses, actor identity/type, UTC timestamp, reason, and correction flag. Administrator/assigned-employee ownership applies. New manual bookings record an administrator creation event; trusted AI bookings record the sender client. Old records receive a migration-time system baseline with a note that earlier details are unavailable. `VISIT_CONFLICT` (409) means the caller's version is stale and they must reload; `INVALID_VISIT_TRANSITION` and `VISIT_TOO_EARLY` also return 409. Invalid payloads/blank correction reasons return 400; unauthorized actors return 403. A restore conflict returns `BARBER_UNAVAILABLE` (409). Cancellation cancels the same invoice, no-show keeps it issued, and corrections away from cancelled restore it to issued. Invoice ID/amounts, payment status, and original window are preserved; no automatic cash refund occurs. The internal client-cancellation service permits only the authenticated sender's own strictly future booked visit (`CLIENT_CANCELLATION_NOT_ALLOWED`, 409 otherwise); WhatsApp wiring remains phase 13, with no public client action endpoint.

Administrator-only `PATCH /api/bookings/:id` accepts a partial edit such as `{ "expectedVersion": 0, "startTime": "10:00", "endTime": "10:20", "adultCount": 2, "reason": "optional nonempty reason" }`. Editable fields are `addressId`, `employeeId`, `date`, `startTime`, `endTime`, `adultCount`, `childCount`, `specialChildCount`, and `notes`; at least one is required. A booked visit that has not started is a reservation edit, and its resulting start must remain strictly in the future. A started or finished visit (no longer `booked`, or its start has passed) is a correction: it requires a `reason`, may be moved into the past, and still rechecks working hours and conflicts. Prices/source/client identity/status cannot be supplied. Window/barber changes recheck working hours, exceptions, enabled status, and conflicts under shared employee locks. A supplied address must belong to the client and snapshots its current saved details; omitted address/barber fields preserve historical snapshots. An edit never changes the agreed cash and link amounts. The transaction retains the booking/reference/invoice IDs, issue time and amounts, and saves complete before/after snapshots with actor/time/reason.

`GET /api/bookings/:id/revisions` returns `{ revisions }` ordered by version, for the administrator or current assigned employee. Reassignment removes the former employee's access to all booking details and histories. `visitVersion` now advances for edits, visit actions, and payment actions; send its latest value as `expectedVersion` for either. Versions in individual visit-event/revision lists can have gaps. Invalid merged counts/windows return `INVALID_INPUT` (400); a reservation edit to a non-future start returns `BOOKING_START_NOT_FUTURE` (400); unavailable windows/barbers return `BARBER_UNAVAILABLE` (409). Stale edits return `BOOKING_CONFLICT` (409); a correction without a reason returns `CORRECTION_REASON_REQUIRED` (400); any `reconciliation` is refused with `RECONCILIATION_NOT_ALLOWED` (409) because an edit never changes the amount; unchanged edits return `BOOKING_UNCHANGED` (409). Missing records return 404 and employee edits return 403. Browser writes require origin/CSRF protection. Any failure rolls back the reservation, invoice, and revision together. The dashboard provides the administrator edit dialog and revision history; WhatsApp rescheduling remains later work.

`POST /api/bookings/:id/payment` is administrator-only and accepts `{ "expectedVersion": 1, "method": "cash" }`, only after arrival/completion. Employees can read the invoice, its status, and the payment history but cannot record a payment. `method` is required and is one of `cash`, `link`, or `knet`. The server records the full current issued invoice amount with that method; callers cannot supply an amount. It returns `{ booking, payment }` (`payment.method` included), advances `visitVersion`, and marks the same invoice paid without changing visit status or prices. One active receipt per invoice is enforced transactionally and by a generated unique database key. `POST /api/bookings/:id/payment/undo` is administrator-only and requires `{ "expectedVersion": 2, "paymentId": "<current receipt uuid>", "reason": "required nonempty reason" }`. It voids the mistaken entry, makes the invoice unpaid, and retains history; it does not record a cash refund. A replacement full receipt follows the same state rules.

`GET /api/bookings/:id/payments` returns `{ payment, payments, events }` for the administrator/current assigned employee. `payment` is the active receipt or null; `payments` includes voided receipts. Receipts retain `originalAmount`, `method`, `recordedBy`, `recordedAt`, and immutable `bookingAtReceipt` with original invoice/barber details; `amount` is the reconciled current amount. Events retain actor/time/reason, previous/new receipt values, shared version, `method`, amount, kind (`recorded`, `voided`, `extra_cash`, `refund`), and the linked invoice-revision ID for adjustments. Reconciliation and undo events carry the receipt's method forward. Undo amounts identify corrected records; they do not represent refunds. Reassignment removes the former employee's access while retaining receipt attribution. Cancellation preserves paid cash/history and creates no refund.

Paid edits need no cash adjustment: since S10 an edit never changes the agreed cash and link amounts, so `reconciliation` is refused (`RECONCILIATION_NOT_ALLOWED`, 409). `extra_cash` and `refund` events recorded before that change stay readable in the payment history. Payments remain one full receipt per invoice, never partial or split.

Payment and paid-edit errors return 409: `PAYMENT_NOT_ALLOWED`, `PAYMENT_ALREADY_RECORDED`, `PAYMENT_CONFLICT`, `PAYMENT_RECORD_MISSING`, `RECONCILIATION_REQUIRED`, `RECONCILIATION_MISMATCH`, or `RECONCILIATION_NOT_ALLOWED`. Invalid input returns 400, missing bookings return 404, and role/ownership/CSRF denial returns 403. All writes require the usual origin/session CSRF protection and latest shared version. No provider, online/partial payment, or public client payment action was added. The dashboard provides administrator full-payment recording with a method picker (default cash), undo of mistaken entries, and read-only payment history for barbers that shows each method; reports render the collected-money split by method.

The salon API is administrator-only: `GET /api/salon?from=&to=&branchId=` returns `{ entries, totals }` for the period, `POST /api/salon` creates one entry per branch and date with `{ "branchId": "<uuid>", "date": "YYYY-MM-DD", "childCount": 3, "cash": "5.000", "link": "1.000", "knet": "2.000" }` (amounts default to `0.000`; the server computes `total`), `PATCH /api/salon/:id` applies a subset edit (requiring the entry's `expectedVersion`) and recomputes the total, and `GET /api/salon/:id/history` returns the before/after events. A duplicate branch+date returns `SALON_ENTRY_EXISTS` (409), a stale version returns `SALON_ENTRY_CONFLICT` (409), and a no-op edit returns `SALON_ENTRY_UNCHANGED` (409); unknown entries/branches return 404, invalid amounts return 400, and a total that overflows the stored precision returns `SALON_TOTAL_TOO_LARGE` (400). Writes require origin/session CSRF. `GET /api/reports/comprehensive?from=&to=` (administrator-only; period only, like the old report, so a `branchId` is rejected) returns `barbers`, one `salon` row, and `totals`, each with per-method `{ count, total }` money, a `collected` total, and a one-decimal `share` of the combined collected total.

Reports (phase 9) are read-only and available to the administrator and employees: `GET /api/reports/reservations` and `GET /api/reports/haircuts`. Both accept `dateBasis` (`visit_date`, the default, or `created_date`, the Kuwait day the reservation was made), inclusive `from`/`to` dates, `employeeId`, `clientId`, `status`, `source` (`manual`/`ai`), and `q` (reference or saved client name/phone). The reservations report also takes `limit` (1–100, default 20) and `offset`, and returns `{ dateBasis, timeZone, summary, bookings, total, limit, offset }`: the summary counts reservations by visit status and source, plus edited reservations/edits and corrected reservations/status corrections; each booking adds `editCount` and `correctionCount`. The haircut report returns adult/child/special-needs quantities as `totals`, `byDate`, and `byEmployee`, each with `bookings`, `reserved` (all matching reservations), `completed`, `open` (booked/arrived), `cancelled`, and `noShow`. Completed quantities come from visit status, independent of payment. Work stays with the barber currently assigned to the reservation; rows show current barber names. Employees always receive only reservations currently assigned to them, and filtering by another barber returns 403. Invalid filters return `INVALID_INPUT` (400).

The barber report (phase 10) uses the same filters and access rules: `GET /api/reports/employees`. Each row has `work` (the haircut measures above plus `completedVisits` and `reservedMinutes`), `invoices` (`issued`, `cancelled`, and `outstanding` = issued and unpaid, each `{ count, total }`), and `cash` (active receipts at their current reconciled amount, including money kept on cancelled visits; voided receipts excluded), which is `{ count, total, byMethod: { cash, link, knet } }` so collected money splits by payment method. Barber rows and the invoice/cash report summary read `cash` from the administrator's daily barber collections instead; those follow only the period and barber filters, so `cash` is `null` there when a client, status, source, search, or payment-status filter is applied. Each invoice entry's `cash` is its own receipt and includes `method`. Money totals are exact three-decimal KWD strings. Reserved minutes cover booked/arrived/completed windows and include travel; cancelled and no-show visits release their window. Barber rows add `enabled` and `availableMinutes`: scheduled working minutes from weekly hours and dated exceptions for every day from `from` to `to`, or `null` unless the visit-date basis has both dates. Employees see only their own row. Individual records come from `GET /api/reports/reservations` with the same filters. The administrator-only salon report (`GET /api/salon`) and comprehensive report (`GET /api/reports/comprehensive`) group collected money by payment method with totals and shares. The administrator-only booking tracking report `GET /api/reports/tracking?from=&to=&employeeId=&clientId=` returns each matching booking (by Kuwait visit date, newest first) with its full timeline oldest first: creation, visit status changes and corrections, reservation revisions, payments, and WhatsApp sends, each with actor name/role, time, and reason; with no period it covers the current Kuwait week (Saturday–Friday), a lone `from` or `to` covers 7 days from or up to that day, and a period longer than 31 days returns 400.

Employee login now rechecks the verified phone as well as enabled status and password hash while locking the account before session creation. An in-progress login with the old phone is rejected if an administrator changes the phone before that step.

## Web dashboard

`apps/web` is an Arabic-only, right-to-left Next.js dashboard for the implemented backend (phases 1–10). Screens: login; bookings list/detail/new booking, visit actions, administrator corrections and edits, administrator cash recording/undo, history tabs, and a printable invoice; clients and addresses; barbers with weekly hours and dated exceptions; branches (for salon entries); the barber’s own schedule and profile; salon daily entries (`/salon`), and reports (`/reports`): bookings with a summary and linked records, haircuts by date/barber, barber performance with reserved versus scheduled hours, client history, the administrator-only booking tracking timeline (`/reports/tracking`), the invoices/cash report, and the administrator-only salon report and comprehensive collections report. Report filters (date basis, range, barber, client, status, source, search) live in the page address, are shared by the four report tabs, and are printed with the report. Employees see only their own bookings and pages; administrator pages show a clear message if opened directly by an employee. The API remains authoritative for every rule.

Design system:

- Tokens live in `apps/web/src/app/globals.css` as CSS variables for light (`:root`) and dark (`.dark`) themes, mapped to Tailwind with `@theme inline`. Components use token classes only (`bg-card`, `text-muted-foreground`, `bg-status-booked-soft`, …), never raw colors. Brand colors: teal primary, sun-yellow accent, cool mist background.
- Typeface: Readex Pro (Arabic + Latin), bundled through `@fontsource-variable/readex-pro` with no external font request. Digits are Western (0–9); phones, amounts, and references render left-to-right inside Arabic text through the `Ltr` component.
- UI primitives are shadcn/ui (Radix) components in `apps/web/src/components/ui`, configured by `apps/web/components.json` with `rtl: true`. Add more with `pnpm dlx shadcn@4.21.0 add <name>` from `apps/web`, then check the import path (`@/lib/utils`) and RTL behaviour.
- Theme: light, dark, or system, via `next-themes`. Print styles always use the light palette.
- Data: TanStack Query hooks in `apps/web/src/lib/api/hooks.ts` call the same-origin `/api` proxy, attach the session CSRF token to writes, sign out on 401, and reload a booking after stale-version conflicts. Forms use react-hook-form with Arabic Zod schemas in `apps/web/src/lib/forms.ts`, built on the shared contracts.
- Money is computed in integer fils (`lib/money.ts`); dates and times are Kuwait-local (`lib/kuwait-time.ts`).

## Docker

`docker.web` builds the Next.js standalone server; `docker.api` builds and packages the Express API with production dependencies. Each image copies only its own app and the packages it uses, installs from manifests first, and keeps the pnpm store (and the Next.js build cache) in BuildKit cache mounts, so an API-only change does not rebuild web, a web-only change does not rebuild the API, and docs/tests edits rebuild nothing. A lockfile change reinstalls dependencies for both. Both run as non-root users. `.dockerignore` excludes secrets and local build/dependency artifacts.

```sh
pnpm docker:up
pnpm docker:down
```

Compose runs its own MySQL 8 container (`db`, data in the `db-data` volume), a one-off `migrate` service that applies Drizzle migrations on every `up`, then the API and web. Following the VPS port convention (web `30x0`, API `40x0`), web is published on `127.0.0.1:3030` for a host reverse proxy and the API on `127.0.0.1:4030` for host-only checks; set `WEB_BIND_ADDRESS`/`WEB_PORT` or `API_BIND_ADDRESS`/`API_PORT` if needed. MySQL is not published to the host. Each service has a memory cap (`db` 768 MB, `migrate` 512 MB, `api` and `web` 384 MB each) so one runaway container cannot exhaust the shared VPS. On the server, `scripts/deploy.sh +965XXXXXXXX` creates `.env.production` with random secrets on the first run (and prints the administrator password once), then builds and starts everything; later runs keep the existing file. Compose needs `DB_PASSWORD`, `DB_ROOT_PASSWORD`, `DOCKER_DATABASE_URL`, and `API_ENV_FILE=.env.production` from that file; the `docker:*` scripts pass it with `--env-file`.

The internal API address is a web build argument, so rebuild web when changing it. Docker is required for image builds and Compose execution.

### Backups

Two named volumes hold state that is not in Git and must both be backed up: `db-data` (MySQL) and `uploads-data` (barber photos under `UPLOADS_DIR=/app/uploads`). `scripts/deploy.sh` documents the per-volume `tar` backup and restore commands in its header; stop the stack before archiving so the MySQL data directory is consistent (or take a logical `mysqldump`), and restore both volumes into a fresh host while the stack is stopped. A database-only backup is incomplete because it omits the photos.
